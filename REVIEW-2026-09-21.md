# KaAlerto — UX, core-feature and system review, 21 Sep 2026

Findings from a read-only review of the LGU dashboard and the Android app. Nothing was changed while producing it. Each finding has an ID (`D` for dashboard, `A` for Android) so it can be referred to in a commit or a task.

**How it was done**

- **Dashboard:** read all 12 source files (about 2,000 lines) and used the running console on live Supabase data (48 events) at 1366×800 and 375 px, measuring the page directly.
- **Android app:** registered a throwaway user ("Test T.") on the Xiaomi (`711c291c`) and walked the map, drawer, shelters, family, role, profile, SOS hold screen and Storm Mode. Report, detail, routes and withdraw were exercised earlier the same day. Also read the code: 130 Kotlin files, 19.3k lines, 239 unit tests.
- **Not done:** no SOS or report was sent. Mesh and QR pairing were not re-proved (`CLAUDE.md` records them as proven on real phones earlier).
- **Status column:** every finding is **open** as of this writing.

---

## 1. Summary

| | Verdict |
|---|---|
| **Dashboard** | A clean, honest, read-only monitoring console. Weak where it matters most: its alarm stops when the tab is not in front, it shows raw events instead of the folded per-spot state the phone shows, and it is a viewer rather than a dispatch tool. |
| **Android app** | More thoughtful than its size suggests. Its principles are visible in the UI (never claims what it cannot know, careful about safety, works offline). Weak points: a crowded map screen, no list of reports, thin accessibility. (A1, the manual role picker, was withdrawn by the project owner.) |
| **Across both** | The dashboard and the phone can disagree about the same events (D2). It is the largest cross-system gap. |

## 2. Dashboard

### 2.1 What works well

- Clear structure: sidebar with stats, tabs and a list; a map with a detail panel; a collapsible sidebar that is `inert` when collapsed.
- Honest copy: "Reconnecting…" on errors, "Expired — needs a fresh look", a routes note that an unreported road can still be flooded, a note that name and medical details are deliberately not sent, and a PIN screen that says it is a shared demo PIN.
- SOS is never buried: open SOS sorts first, and the tab title shows the open count.
- Alerts: Web Audio siren (no sound file), notification permission requested from an explicit click, a baseline on first load so old data does not shout, two tones for SOS and S3.
- Photos are proxied with a validated hash; the PIN check stays on the server.
- Accessibility basics: one `h1`, `lang` set, labelled controls, a live region, a reduced-motion rule.
- No overflow at 375 px (upgrade item 10).

### 2.3 Against PRD §7.10

| Planned | State |
|---|---|
| Live area-wide map, same severity and staleness encoding | Built (raw events, not folded — D2) |
| Rescue queue | A list; no grouping and no actions |
| Degraded state when unreachable | Built ("Reconnecting…") |
| Post-event export | Partial (CSV of the filtered tab) |
| Evacuation capacity management | Read-only status view only |
| Accounts, audit log, official verification, grouped incidents | Not built |

### 2.4 System and code quality

- Small files with useful comments, strict TypeScript, clean type-check and build.
- **No automated tests** for the dashboard. The pure logic (`items.ts`, `routing.ts`, `evac.ts`) has only had one-off scripts run against it.
- **Drift risk:** four hand-ported copies of phone logic (SOS fold, withdrawal, routing, shelter fold) plus a copy of the shelter fixture. Nothing tests that they agree.

### 2.5 Accepted risks (not recommended for change)

- The PIN is shared, unlimited and demo-only, and the anon key ships in the app. Settled on 19 Sep ("do not touch"); the PIN screen says so plainly.

## 3. Android app

### 3.1 What works well

- **Crisis-appropriate SOS.** The hold screen needs a long press, shows exactly what will be sent (place name, coordinates ±17 m, time), says details can be added afterwards, uses a dark low-glare palette and a plain cancel. SOS is also reachable from the registration screen.
- **Honest empty states.** "Wala pang bukas na silungan ngayon…", the Family screen's "nasa mga phone lang, hindi ina-upload", the profile SMS field's "hindi pa gawa", and a note on reports that they may be incomplete or out of date.
- **Offline-first is visible.** Connection status, report count, mesh line, offline pack. Routes fail cleanly in airplane mode with no fake result.
- **Registration.** Two name fields, GPS-filled place name, an amber warning outside the demo area, a note that the name is visible to others.
- **Drawer.** Five destinations, a Filipino/English toggle, and a footnote saying Storm Mode and SOS are on the main screen.
- **Storm Mode.** Re-tints the whole map dark and leaves the app's own layers alone.
- **Today's work** (withdraw, confirm prompt, routes) was verified on the device.
- **Code.** One package per feature, comments that record real incidents, pure logic separated and unit-tested (239 tests, weighted toward SOS 48, data 47, identity 30, family 29). Every string goes through `tr()`; only 7 raw literals remain.

### 3.4 Additional features

- **Mesh:** designed, proven earlier on two real phones; only protocol logic is unit-tested (16 tests).
- **Family circles:** clean screen; the QR step on real hardware is still unproven.
- **Roles and evacuation centres:** built. Roles use the manual picker on purpose (see A1).
- **Routes:** works; disclosed, with a clean offline fallback.
- **Filipino/English toggle:** applied across the app.

### 3.5 System and code quality

- **Big files:** `MapScreen.kt` (1,281 lines), `KaAlertoApp.kt` (797) and `DetailSheet.kt` (757). `KaAlertoApp` is a hand-written screen switch rather than a navigation graph; the comments say this was deliberate, but back-stack and deep-link behaviour is all custom code.
- **Testing:** JVM unit tests only. No `androidTest` directory, so no UI or on-device automation.
